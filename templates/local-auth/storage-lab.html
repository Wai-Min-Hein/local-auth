Browser Storage Lab

Learn how localStorage really behaves

This page explains what localStorage and sessionStorage are, how long they live, where they are useful, and why this auth-localstore feature uses both in different ways. It also includes a lab so you can test browser storage behavior yourself instead of just reading about it.

What they store Small key-value strings inside the browser for one specific site origin.
Different lifetimes localStorage persists across tab close. sessionStorage is meant for the current tab session.
When they end localStorage ends when cleared. sessionStorage ends when the tab session ends.

What Is localStorage?

localStorage is a built-in browser storage area for saving small pieces of data as key-value pairs. Both the key and the value are stored as strings.

Each website origin gets its own storage bucket. That means one site cannot read another site's local storage values. 

localStorage.setItem('theme', 'dark');

const theme = localStorage.getItem('theme');
// 'dark'

localStorage.removeItem('theme');

Lifetime: The Key Idea

localStorage survives tab close.

If you save data in one tab, close that tab, then open the same page again later, the data should still be there.

sessionStorage does not behave the same way.

sessionStorage is tied to the current browser tab or window session. Once that tab is fully closed, the session data is usually gone.

localStorage vs sessionStorage

Feature localStorage sessionStorage
Lifetime Persistent until removed or cleared Cleared when the tab/window session ends
Survives refresh Yes Yes
Survives tab close Yes No, usually not
Good for Saved preferences, cached small app data, simple persistent demos Temporary logged-in tab state, current session flow, one-tab interactions

Real-World Usage Examples

Good fits for localStorage

  • Remembering theme choice like light mode or dark mode.
  • Saving draft text in a notes app.
  • Persisting onboarding completion flags.
  • Small demo apps where a database does not exist yet.

Bad fits for localStorage

  • Highly sensitive secrets such as real auth tokens in production.
  • Large files or large datasets.
  • Data that must be shared securely across devices.
  • Anything that requires server trust.

How This Feature Uses Browser Storage

In the current auth-localstore feature, registered users are saved in localStorage under the key users. That makes sense because registered users should still exist after refresh, navigation, tab close, and browser restart. 

[
  {
    "username": "alice@example.com",
    "displayName": "Alice",
    "password": "Abc$1234"
  }
]

The active logged-in user is saved in sessionStorage under the key currentUser. That matches the feature spec because the login session should end when the user closes the browser tab. 

{
  "username": "alice@example.com",
  "displayName": "Alice"
}
Why the split matters

Persistent account list in localStorage, temporary active session in sessionStorage. That is the exact storage design used by this lesson's auth flow.

Detailed Instructions for Testing Lifetime

  1. Select localStorage, enter a key such as labNote, then save a value.
  2. Switch to sessionStorage, use a different key such as labSession, then save another value.
  3. Load both values again and confirm both exist.
  4. Refresh the page and load both again. Both should still exist after refresh.
  5. Now fully close this tab.
  6. Open the same page again in a new tab.
  7. Load the localStorage key. It should still exist.
  8. Load the sessionStorage key. It should now be missing.
  9. That proves localStorage survives tab close, while sessionStorage is limited to the tab session.
  10. Finally, click Remove key or Clear lab keys in both, then load again to verify explicit removal.
